一、综合知识（上午客观题）

1. 软件架构风格 ★★★★★

速记口诀： 「管事分微仓客浏」（管道-过滤器 / 事件驱动 / 分层 / 微内核 / 仓库黑板 / C/S / B/S）

七大架构风格对比表

架构风格 核心思想 优点 缺点 典型应用
管道-过滤器 数据流经一系列独立的过滤器组件，每个过滤器完成特定变换 松耦合、可复用、支持并发 批处理语义、不适合交互系统、数据转换开销大 Unix管道、编译器、数据ETL
事件驱动 组件通过发布/订阅事件进行异步通信，解耦生产者与消费者 高解耦、异步处理、扩展灵活 调试困难、执行顺序不确定、事件风暴风险 GUI框架、消息队列（Kafka）、IoT
分层 系统分为若干层，每层只与相邻层交互，上层调用下层服务 职责清晰、易维护、可替换单层 性能损耗（数据需逐层传递）、过度设计风险 OSI网络模型、Spring MVC、三层架构
微内核 内核只保留最小功能，扩展功能以插件形式动态加载 灵活扩展、核心稳定、插件独立部署 插件通信开销、插件质量参差 Eclipse IDE、操作系统微内核、VS Code
仓库/黑板 共享数据仓库（黑板）居中，各知识源组件共同读写 便于知识共享、知识源相互独立 黑板成为瓶颈、数据一致性难保证 AI专家系统、语音识别、编译器符号表
C/S 客户端发起请求，服务器提供服务，两层结构 界面丰富、响应快、安全性高 客户端部署维护成本高、升级困难 传统桌面应用、数据库客户端
B/S 浏览器作为统一客户端，通过HTTP访问服务器 零安装、跨平台、易维护 交互体验弱于C/S、服务器压力大 Web应用、SaaS系统、企业门户

🔬 费曼解释：管道-过滤器

想象一条工厂流水线：原料（数据）从传送带左端进入，经过打磨（过滤器A）→ 喷漆（过滤器B）→ 检测（过滤器C）后成品从右端流出。每个工位（过滤器）只专注自己的工序，不关心前后是谁；传送带（管道）只负责搬运，不加工。这就是管道-过滤器：数据流动，逻辑分段，各司其职。

⚠️ 避坑指南

  • 管道-过滤器≠流式处理框架（Flink/Spark是实现，不是架构风格本身）
  • 事件驱动架构中，事件是”通知”而非”命令”——发布者不关心谁消费
  • B/S是C/S的特例，但考题中常对立出现，选”瘦客户端/免安装”优先选B/S
  • 微内核架构的”内核”极小，大量功能靠插件——Eclipse是典型，不是分层架构

2. 操作系统基础 ★★★★

进程调度算法对比

速记口诀：”先短优轮多反馈”

算法 全称 核心规则 优点 缺点 是否抢占
FCFS 先来先服务 按到达顺序执行 公平、简单 护航效应（短作业等长作业） 否
SJF 短作业优先 执行预计时间最短的 平均等待时间最短 长作业饥饿、需预知执行时间 否（SRTF为抢占版）
优先级 Priority 优先级高者先执行 灵活、支持紧急任务 低优先级饥饿（需老化机制） 可抢占/不可抢占
RR 时间片轮转 每进程分配固定时间片 公平、响应快 时间片设置敏感、上下文切换开销 是
多级反馈队列 MLFQ 多个优先级队列，降级机制 兼顾短作业与长作业 实现复杂 是

死锁四个必要条件

速记口诀：”互不请循”

条件 含义 破坏方法
互斥 资源一次只能被一个进程占用 将资源改为共享（如打印机虚拟化）
不可剥夺 进程持有资源不能被强制夺走 允许抢占（保存状态后剥夺）
请求保持 进程持有资源同时等待新资源 一次性申请所有资源
循环等待 进程形成资源等待环 资源编号，按序申请

页面置换算法对比

算法 规则 缺页率 特点
OPT 置换将来最长时间不用的页 最低（理论最优） 理想算法，实际不可实现
FIFO 置换最先进入的页 较高 简单，存在Belady异常
LRU 置换最近最久未使用的页 较低 近似OPT，无Belady异常
Clock 近似LRU，用访问位循环扫描 中等 工程常用，实现简单

⚠️ 避坑指南

  • Belady异常：增加内存帧数反而导致缺页率升高，仅FIFO存在此异常，LRU/OPT不存在
  • SJF平均等待时间最短≠总体最优（长作业可能饥饿）
  • RR时间片太小→上下文切换开销大；太大→退化为FCFS

3. 数据库设计 ★★★★★

范式速记口诀： 「一原子、二非主、三非传」

  • 1NF：每列原子（不可再分）
  • 2NF：非主属性完全依赖主键（消除部分依赖）
  • 3NF：非主属性不传递依赖主键（消除传递依赖）
  • BCNF：每个决定因素都是候选键

ACID属性详解

属性 全称 含义 Feynman解释
A 原子性 Atomicity 事务全做或全不做 转账要么两账户都变，要么都不变，不存在”扣了但没收到”
C 一致性 Consistency 事务前后数据库状态合法 转账前后两账户总额不变，业务规则始终满足
I 隔离性 Isolation 并发事务互不干扰 两人同时转账，各自看到的是完整的中间状态
D 持久性 Durability 已提交事务永久生效 提交后即使断电，数据也不丢失（靠WAL日志保证）

事务隔离级别对比

隔离级别 脏读 不可重复读 幻读 说明
读未提交 READ UNCOMMITTED ✅ 会发生 ✅ 会发生 ✅ 会发生 性能最高，一致性最差
读已提交 READ COMMITTED ❌ 解决 ✅ 会发生 ✅ 会发生 Oracle默认级别
可重复读 REPEATABLE READ ❌ 解决 ❌ 解决 ✅ 会发生 MySQL InnoDB默认
串行化 SERIALIZABLE ❌ 解决 ❌ 解决 ❌ 解决 性能最差，一致性最强

⚠️ 避坑指南

  • 脏读=读了别人未提交的数据；不可重复读=同一事务两次读同一行结果不同；幻读=同一事务两次查询行数不同
  • MySQL可重复读通过MVCC+Gap Lock基本解决幻读，但理论上不完全
  • 2NF只针对复合主键场景，单列主键自动满足2NF

4. 系统安全 ★★★★

加密算法三类对比

类别 代表算法 密钥 速度 用途
对称加密 AES、DES、3DES、RC4 加解密同一密钥 快 大数据加密、文件加密
非对称加密 RSA、ECC、ElGamal 公钥加密，私钥解密（或反之） 慢 密钥交换、数字签名
哈希算法 MD5、SHA-1、SHA-256 无密钥（单向） 极快 完整性校验、密码存储

数字签名流程

防火墙类型对比

类型 工作层次 过滤依据 优点 缺点
包过滤防火墙 网络层（L3） IP、端口、协议 速度快、开销小 无状态、无法检测应用内容
状态检测防火墙 网络层+传输层 连接状态表 安全性高于包过滤 性能略低
应用代理防火墙 应用层（L7） 应用协议内容 最强安全性、深度检测 速度慢、每种协议需独立代理
下一代防火墙(NGFW) 全层次 应用识别+用户+内容 全面防护 成本高

⚠️ 避坑指南

  • 数字签名 ≠ 加密：签名用私钥签、公钥验；加密用公钥加密、私钥解密——方向相反！
  • MD5、SHA-1已被认为不安全（存在碰撞攻击），应使用SHA-256及以上
  • SSL/TLS握手阶段用非对称加密交换会话密钥，正式传输用对称加密（兼顾安全与速度）

5. 系统可靠性 ★★★★★

核心公式

指标 公式 含义
MTBF 平均无故障时间 = 总运行时间 / 故障次数 系统相邻两次故障的平均时间间隔
MTTR 平均修复时间 = 总修复时间 / 修复次数 从故障发生到恢复的平均时间
可用性 A A = MTBF / (MTBF + MTTR) 系统正常运行时间占总时间的比例
串联可靠性 R = R₁ × R₂ × … × Rₙ 所有组件都正常，系统才正常
并联可靠性 R = 1 − (1−R₁)(1−R₂)…(1−Rₙ) 至少一个组件正常，系统即正常

🔬 费曼解释：串联 vs 并联

串联像一根链条——哪个环节断，整体就断。三个可靠性均为0.9的组件串联：
R = 0.9 × 0.9 × 0.9 = 0.729（比最弱的还低！）

并联像备用发动机——至少一台工作，飞机就能飞。三个0.9的组件并联：
R = 1 − (0.1 × 0.1 × 0.1) = 0.999（大幅提升！）

6. 软件质量属性 ★★★★★

ISO 25010八大质量特性速记： 「功效兼用可维安移」
= 功能性 / 效率（性能）/ 兼容性 / 易用性 / 可靠性 / 维护性 / 安全性 / 可移植性

质量属性场景六要素

速记口诀： 「激来响环制满」

要素 含义 示例
激 刺激（Stimulus） 触发事件 用户发起1000并发请求
来 刺激源（Source） 事件来自何处 外部用户
响 响应（Response） 系统的反应 在2秒内返回结果
环 环境（Environment） 发生的上下文 正常运行状态下
制 制品（Artifact） 受影响的系统部分 订单查询模块
满 响应度量（Measure） 如何量化响应 99%请求响应时间≤2s

⚠️ 避坑指南

  • 性能（Performance）≠可靠性（Reliability）：性能关注速度，可靠性关注故障率
  • 可修改性（Modifiability）是维护性的子特性，是架构评估ATAM的重要质量属性
  • 安全性包含：机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）——即CIA三元组

7. 设计模式 ★★★★

23种设计模式速记： 「创五结七行十一」

  • 创建型（5种）：工厂方法、抽象工厂、单例、建造者、原型
  • 结构型（7种）：适配器、桥接、组合、装饰器、外观、享元、代理
  • 行为型（11种）：职责链、命令、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者、解释器

高频模式详解

模式 类型 核心意图 典型场景 关键词
工厂方法 创建型 定义创建对象的接口，子类决定实例化哪个类 日志记录器、数据库连接 延迟实例化、子类决定
单例 创建型 确保类只有一个实例，并提供全局访问点 配置管理、线程池、缓存 全局唯一、双重检查锁
观察者 行为型 对象间一对多依赖，一个变化通知所有依赖者 事件监听、MVC中Model通知View 发布订阅、解耦通知
策略 行为型 定义一系列算法，封装每个算法，使其可互换 排序算法选择、支付方式切换 算法族、运行时切换
装饰器 结构型 动态地给对象添加额外职责，比继承更灵活 Java I/O流、Web中间件 透明包装、动态增强

⚠️ 避坑指南（代理 vs 装饰器）

  • 代理模式：控制访问（权限控制、远程代理、缓存代理），代理与被代理对象实现同一接口，代理不改变行为
  • 装饰器模式：增强功能（动态添加职责），装饰器和被装饰对象实现同一接口，重点在”叠加功能”
  • 记忆口诀：代理管门卫（控制访问），装饰穿新衣（增强功能）

10. 分布式与云计算 ★★★★

CAP定理

速记： CAP三者只能同时满足其中两个

属性 全称 含义
C 一致性 Consistency 所有节点同一时刻看到相同数据
A 可用性 Availability 每个请求都能收到响应（不保证最新数据）
P 分区容错性 Partition Tolerance 网络分区时系统仍能运行

🔬 费曼解释：CAP

两个城市各有一个银行分支，通过网络同步账户余额。

  • 网络断了（分区），要么等网络恢复再返回结果（保C放A），要么立即返回可能过时的数据（保A放C）。
  • 网络不可靠是分布式系统的常态，所以P必须保留。
  • 实际选择：CP系统（ZooKeeper、HBase）强调一致性；AP系统（Cassandra、Eureka）强调可用性。

BASE理论

BASE是对CAP中AP系统的工程实践，放弃强一致性换可用性：

  • BAsically Available（基本可用）：允许损失部分可用性
  • Soft state（软状态）：允许数据存在中间状态
  • Eventually consistent（最终一致性）：最终所有节点数据一致

云服务模型对比

模型 全称 用户管理 提供商管理 典型产品
IaaS 基础设施即服务 OS+中间件+应用 硬件+网络+虚拟化 AWS EC2、Azure VM
PaaS 平台即服务 应用+数据 OS+运行时+中间件 Google App Engine、Heroku
SaaS 软件即服务 数据配置 全栈 Salesforce、Office 365

⚠️ 避坑指南

  • 分布式系统中P（分区容错）几乎是必须的，实际是在C和A之间权衡
  • BASE≠ACID的对立面，是互补关系——关键业务用ACID，高并发场景用BASE
  • IaaS/PaaS/SaaS区别记忆：用户管理的”越来越少”，控制权越来越低

数据类型 底层结构 适用场景 常用命令

缓存三大问题对比

速记口诀： 「穿透查无/雪崩同时/击穿热点」

问题 现象 根本原因 解决方案
缓存穿透 大量请求查询不存在的数据，每次都打到DB 恶意攻击或业务BUG ① 布隆过滤器拦截；② 空值缓存（TTL短）
缓存雪崩 大量缓存同时失效，DB瞬间承受海量请求 批量缓存设置相同TTL ① TTL加随机值；② 多级缓存；③ 熔断限流
缓存击穿 单个热点key失效，大量并发直接打到DB 热点数据缓存过期 ① 互斥锁（Mutex Lock）；② 逻辑过期（不设TTL）

分库分表策略

策略 适用场景 优点 缺点
垂直分库 按业务模块拆分 解耦业务 跨库join复杂
垂直分表 宽表拆分（冷热字段分离） 减少IO 同一业务需多次查询
水平分库 数据量大，单库存不下 扩展性强 分布式事务复杂
水平分表 单表数据量超千万 查询加速 数据迁移复杂

⚠️ 避坑指南

  • 缓存穿透=查不存在的key；缓存击穿=热点key过期；缓存雪崩=大量key同时过期——三者易混淆
  • 分库分表后无法使用跨库事务，需用分布式事务（Seata/TCC/SAGA）替代
  • Redis持久化：RDB（快照，恢复快）vs AOF（日志，数据更安全）→生产建议RDB+AOF混合

4. Web架构设计 ★★★★

负载均衡算法对比

算法 原理 优点 缺点 适用场景
轮询（Round Robin） 依次分配到每台服务器 简单公平 不考虑服务器性能差异 服务器性能均等
加权轮询 按权重比例分配 考虑性能差异 配置复杂 服务器配置不同
随机 随机选择服务器 简单 分布不均匀 低并发场景
最少连接（Least Connection） 选当前连接数最少的 动态均衡 需维护连接计数 长连接场景
IP Hash 对客户端IP哈希取模 同一客户端固定服务器 服务器故障影响特定用户 需要会话保持的场景
一致性哈希 哈希环，最近节点处理 节点增减影响小 实现复杂 分布式缓存

⚠️ 避坑指南

  • IP Hash能解决Session一致性问题（同一用户始终到同一服务器）
  • 一致性哈希解决缓存节点增减时大量缓存失效的问题（只影响相邻节点数据）
  • 最少连接适合请求处理时间差异大的场景（如文件上传和普通API混合）

5. 微服务架构 ★★★★★

微服务拆分原则

速记口诀：”单业接数自独部”

  1. 单一职责：每个服务只做一件事
  2. 业务边界：按业务领域拆分（DDD领域驱动）

  5. 自治：独立部署、独立技术栈

组件 作用 代表产品

  • 微服务不是银弹：服务数量多时运维复杂度指数级上升，小团队慎用
  • 服务拆分原则：按业务能力（不是技术层）拆分；单一职责；高内聚低耦合

高频易错对比速查表

概念A 概念B 核心区别
数字签名 加密 签名=私钥签+公钥验（不可抵赖）；加密=公钥加+私钥解（机密性）——用途不同
缓存穿透 缓存击穿 穿透=key不存在；击穿=热点key过期
缓存击穿 缓存雪崩 击穿=单个热点key；雪崩=大量key同时过期
串联 并联 串联R=连乘（越乘越小）；并联R=1-连乘余数（越算越大）
ATAM SAAM ATAM多质量属性权衡；SAAM侧重可修改性
风险点 权衡点 风险点=单一负面影响；权衡点=影响多个质量属性（有得有失）
组合 聚合 组合生命周期绑定，部分依赖整体；聚合可独立存在
include extend include必然执行；extend条件触发（可选）
SOA 微服务 SOA用ESB集中总线、粗粒度；微服务去中心化、细粒度
RTO RPO RTO=恢复时间目标（停多久）；RPO=恢复点目标（丢多少数据）
IaaS PaaS IaaS提供虚拟机（用户管OS）；PaaS提供运行平台（用户只管应用）
脏读 不可重复读 脏读=读未提交数据；不可重复读=同事务两次读同行结果不同
不可重复读 幻读 不可重复读=行内容变化；幻读=行数变化（INSERT/DELETE）
FIFO LRU FIFO存在Belady异常；LRU不存在，近似最优
CAP的C ACID的C CAP-C是分布式一致性（所有节点同一时刻数据相同）；ACID-C是事务一致性（业务规则满足）——含义不同！
